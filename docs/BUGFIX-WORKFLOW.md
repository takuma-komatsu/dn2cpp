# リポジトリの標準作業ワークフロー

本書はこの repository のすべての作業に適用する。バグ修正、機能追加、
refactor、テスト、文書・設定の変更、調査、レビューを含み、依頼で本書の
名前やレビュー手順を明示する必要はない。

通常の変更依頼は、その対象の調査・実装・回帰・文書更新・関連検証・独立
レビューと修正・commit・push・PR 作成または更新まで進める依頼として扱う。
本書自体の編集も同様とする。ユーザーが「調査だけ」「commit しない」など
範囲を限定した場合はその指示を優先し、質問・調査・レビューだけの依頼から
変更や PR 作成を始めない。依頼範囲外の作業へ広げない。

単発の変更依頼は PR 作成または更新までで完了する。merge はユーザーが
依頼した場合に行い、継続的な Issue 対応はその開始を依頼された場合だけ
行う。すでに許可された範囲の通常操作について確認を繰り返さない。

ビルド・gate・module 境界・コード規約は [AGENTS.md](../AGENTS.md)、
merge に必要な検証は [CONTRIBUTING.md](../CONTRIBUTING.md) に従う。
本書は作業の進め方を定め、これらの細則を置き換えない。

## 着手と対象

変更作業の開始時は作業ツリーの状態を確認し、既存の作業を保持する。
新規の変更は最新の main を基点に作業ブランチを用意し、既存 PR の続きは
そのブランチで進める。無関係な変更を差分や commit に混ぜない。
AGENTS.md、CONTRIBUTING.md、[README.md](../README.md)、
[ARCHITECTURE.md](ARCHITECTURE.md) を実際に読む。Claude は
[CLAUDE.md](../CLAUDE.md) の import も読む。

依頼から問題、範囲、受け入れ条件、検証方法を確認する。対象 Issue があれば
本文と関連する Issue・PR を読み、不足する情報を対象 Issue に追記する。
Issue がない明確な変更依頼は、その範囲で進めてよい。変更依頼では方針の
提示だけで止まらず実装へ進む。

## 担当と独立レビュー

親セッションは調査・調整・統合・検証を担当し、コード・テスト・文書の
実装は AGENTS.md の指示どおりサブエージェントへ委譲する。指定がなければ、
実装サブエージェントは親セッションと同じモデルおよび reasoning effort
（思考強度）を用いる。同じ変更の実装担当とレビュアーへの委譲は可能だが、
書込みの担当を明確にし、同じファイルや artifact への競合を避ける。

実装と関連検証の完了後、独立した reviewer に実際にレビューを委譲する。
PR 作成前、および既存 PR の変更を完了として報告する前に実施する。
reviewer は原則として独立した単一エージェントとし、複数モデルによるレビューは
ユーザーが明示した場合だけ行う。レビュー候補と reasoning effort は
**Opus / xHigh (`xhigh`)**、**Astra / Max (`max`)**、**Argon / High (`high`)**
に限る。各モデル系列の最新版を使い、具体的なバージョンには固定しない。
Argon は低優先度とする。

可能な限り、実装に使用したモデルとは異なる企業のモデルを優先する。
別企業の候補を利用できない場合は、上記候補内の同企業モデルを独立した
reviewer として使用してよい。**Dots では Astra / Ultra (`ultra`) 固定**とし、
別企業優先や一般の候補選択より優先する。

自己レビュー、上記以外のモデル、指定と異なる思考強度で代用しない。
適用されるモデル・思考強度を利用できない場合、レビュー条件を達成済みとせず、
PR 作成や変更完了の報告、merge へ進まずに不足条件を報告する。

レビューは再現・根拠のある正しさ、デグレ、必要な回帰、repository invariant
に絞る。テスト追加の要求にも下記の基準を適用し、既存の検証では見逃す
具体的な不具合・仕様を示せない場合は要求しない。
無関係な refactor、仕様拡大、些末な style 修正、収拾がつかなくなる
要求を追加しない。main 由来の既存未対応と PR が導入した不具合を区別する。
当該 PR の不具合は必ず直し、関連検証を行ってから全差分を再レビューする。
担当 reviewer の指摘がゼロになるまで繰り返す。指摘を採用しない場合も根拠を
reviewer に示して再評価を受け、未解決の指摘を黙って解決済みにしない。
PR 作成・変更完了の報告・merge の前に、新規ファイルを含む実際の最終差分が
担当 reviewer のレビュー対象であることを確認する。複数モデルのレビューを
明示された場合は、全 reviewer が最終全差分を確認し、全員の指摘がゼロになる
ことを完了条件とする。

## 再現・修正・検証

**コンパイル回数の最小化を最優先し、網羅性のために gate 全体の実行時間を
増やさない。** 原則として gate ごとに集約プログラムを一度だけビルドする。
これは必要な managed build、transpile、native build の各段階を一巡する意味で、
case・引数・入力の差は同じ binary の実行で検証する。同じ binary では検証できない
必須のコンパイル時の差異だけを追加 build の例外とし、網羅性だけを理由に
driver・fixture・再 build を増やさない。重複した build・setup を統合し、
新しい gate へコストを移さない。
変更した gate の build 回数を変更前後で比較し、必要に応じて実行時間も確認する。
必須検証や parity・oracle は弱めない。

変更の性質に応じた検証を選び、commit 前に関連 build と適用される gate を
実行する。バグ修正では修正前の失敗を確認する。**回帰テストの追加を既定の
作業にしない。** まず既存の case と gate を調べ、対象の不具合や変更後の挙動を
検証できるなら、それを実行し、同じ検証を追加しない。

追加は、再現した不具合や新規・変更した挙動について、既存の検証では不足する
具体的な点を説明できる場合に限る。その不足を検出する最小限の case を既存の
case または近い bucket に組み込み、バグの回帰は修正前に失敗することを確かめる。
推測だけの edge case、重複する組合せ、実装をなぞるだけのテストを追加しない。
新規 bucket・fixture・gate は、既存の構成では必要な検証ができない場合に限る。

.NET parity を扱う場合は .NET の実際の挙動を先に確認し、修正後は CLR の
実出力との parity を確認する。block を追加した場合は実行された証拠と、
旧全体出力が unchanged prefix として残ることも確認する。テストや期待出力を
実装に都合よく変えて通さない。意図した既存 divergence の扱いも AGENTS.md に従う。
文書・設定の変更は、参照先、記述の整合性、影響する手順や設定の妥当性を
確認する。文書・コメントのみの変更や挙動を変えない refactor 自体を理由に
回帰テストを追加しない。関連する既存の検証を使う。

検証中は source や checkout を変更しない。build・gate・実行で書込みを行う
プロセス（writer）の終了を確認し、セッションを回収してから次の編集や
checkout、commit 整理へ進む。

main の潜在バグを見つけた場合、確実に直せる関連の些末なものは同時に修正
する。リスクが高いものは再現・原因・必要な対応・受け入れ条件・検証方法を
この repository の GitHub Issues に新規起票する。必要な host や
SDK、先行する変更があれば併記する。Issue は実装の merge と必要な検証が
終わるまで open に保つ。受理や PR 作成だけでは閉じない。残作業を別の Issue に
分け、コードや設計文書には長期に必要な制約を invariant として残す。廃止した
STATUS の旧チケット ID を再利用・引用しない。

## commit と PR

ブランチで導入したバグやデグレの修正は amend し、必要なら interactive
rebase で既存の該当 commit に統合する。追加の fix commit を最終履歴に残さず、
commit は必要最小限の理想的な形に整理する。push 済みの amend は
force-with-lease を使う。PR 本文やコメントにも修正経緯を書かない。

PR の title は英語、本文は簡潔な日本語とする。本文には最終的な挙動と、
変更の評価に必要な回帰範囲・実質的な未検証事項だけを記載する。作業経緯、
amend 履歴、レビューや gate の実行状況、自明な検証対象外・skip 理由、
人間専用手順の未実施注記は書かない。対象 Issue があればリンクし、closing
keyword は merge 時点で完全に解決する対象だけに付ける。

## 完了と merge

必須条件を満たせず進めない場合は、不足している条件と現在の状態を正直に
報告し、pass や変更完了、merge 済みとして扱わない。途中引継ぎファイルは
作らず、現在の PR・branch・HEAD・進捗を本書に固定しない。

必要なローカル検証、最終 head の必須 CI 成功、最終差分に対する独立 reviewer
の指摘ゼロを確認してから rebase merge する。hosted smoke CI だけを merge の
根拠にしない。skip や中断を pass と扱わない。実際に MERGED になったことを
確認する。PR が自動 close しない対象も、必要な検証を確認してから解決した
Issue だけを閉じる。単発の merge 依頼はここで完了する。

## 継続的な Issue 対応

[GitHub Issues](https://github.com/takuma-komatsu/dn2cpp/issues?q=is%3Aissue%20is%3Aopen)
のバグ修正を継続する依頼は、各対象について上記の変更手順から rebase merge
まで進め、次の対象へ移る依頼として扱う。本書を読む・編集する・レビューする
依頼だけではこの継続ループを開始しない。

open Issue を確認し、優先度、依存関係、再現・検証に必要な環境を踏まえて
高優先度バグから対象を選ぶ。着手順と PR の粒度は担当者が判断する。
小さい複数 Issue を同じ PR にまとめてよいが、その中でも順次実装・確認する。
継続ループ内で異なる Issue や PR の実装は並行せず、現在の PR が実際に
merged になるまで次の PR の対象へ着手しない。merge 後は main を更新し、
open Issue を再確認してから次の対象へ進む。

通常操作ごとの確認を繰り返さず、ユーザーの中断・停止指示か修正可能な対象が
なくなるまで継続する。ひとつの PR の完了や待ち時間だけでループを終了しない。

通常の変更依頼例:

> この不具合を修正してください。

継続作業の開始依頼例:

> GitHub Issue の高優先度バグの修正を継続してください。
